Streamlit Canary User Manual

Streamlit Canary User Manual

Streamlit Canary is a fork of Streamlit with an event-driven runtime and a new component library called Components V3. It keeps Streamlit’s familiar look and feel, but removes the rerun cycle that makes large apps slow.

The application function runs once. It builds a persistent component tree, and every later interaction is routed to a signal handler on the server. Only the values that actually changed are sent back to the browser as small patches, and the page updates in place.

What makes it different

StreamlitStreamlit Canary (V3)
Execution modelThe script reruns on every interactionThe app function runs once
UI updatesA new render tree is diffed on every rerunA delta patch updates the affected DOM nodes
Statest.session_state is rebuilt on each rerunState holds Property objects for the session
WidgetsReturn values from the last runExpose reactive Property fields and Signals
Cost of one clickProportional to the whole scriptProportional to the handlers that listen to it

Highlights

  • Performant by design. The app function runs once. An interaction executes only the handlers attached to it, then patches the DOM. The script never re-runs.
  • Reactive, polished event-driven syntax. sc.bind and sc.bbind build derived and two-way values, on_change and component signals attach handlers, and a forced notification (set(value, notify=True)) refreshes output when the value itself did not change.
  • Desktop windows. sc.run(..., show_window=True) serves the app and opens it in a native pyapp-window window, sized in CSS pixels.
  • Custom components included. Folder trees, PathInputBrowse, a PDF viewer, a live log panel, animated toasts, and the rest of the V3 library ship with the package.
  • dunder_literal. PageConfig(dunder_literal=True) keeps names such as __init__ and __name__ from turning into bold text.
  • Fewer dependencies. The core does not require pandas, NumPy, SciPy, pyarrow, or Altair. Altair is needed only if you use AltairChart.

Installation

pip install streamlit-canary

Python 3.11 or newer is required.

Note

Streamlit Canary 0.5.0 is the event-driven API, and it is the default: the components are exported at the top level (sc.Button, sc.Text, sc.Row, …).

Two earlier generations are no longer part of sc:

  • the V1 wrappers (Streamlit component wrappers, rerun model) now live in streamlit_canary.legacy_streamlit_wrappers;
  • the V2 experiment has been removed.

sc.v3.* still resolves, but it is deprecated and warns – the prefix goes away in a later release.

Hello world

import streamlit_canary as sc


class State(sc.State):
    count = sc.Property(0)


state = State()


def app():
    sc.PageTitle('Click Counter')

    with sc.Row('center'):
        with sc.Text('Click count: 0') as txt:
            @state.count.on_change
            def _():
                txt.text.set('Click count: {}'.format(state.count.get()))

        with sc.Button('Increase counter', type='primary') as btn:
            @btn.on_click
            def _():
                state.count.set(state.count.get() + 1)
                # or a shorthand form: state['count'] += 1


if __name__ == '__main__':
    sc.run(app, port=2201)

Save the file and run it with python app.py. Open http://localhost:2201, then click the button. The text changes without a page reload, and app() is not called again.

Running Apps

sc.run starts a Streamlit Canary app. It accepts either the app function itself or a path to a script or module.

import streamlit_canary as sc


def app():
    sc.PageTitle('Hello')
    sc.Text('This page has no rerun loop.')


if __name__ == '__main__':
    sc.run(app, port=2201)

It returns a pair:

server_process, window_process = sc.run(app)

Either element may be None when that process does not exist.

Callable targets

A callable is served in the current process:

sc.run(app, port=2201)

With blocking=True (the default), run() does not return until the server stops. With blocking=False, the server is started on a daemon thread and run() returns at once; the caller must keep the process alive.

Path targets

A .py path is launched in a child process:

sc.run('app.py', port=2201)

A module path is launched with python -m:

sc.run('my_project.app', port=2201)

Arguments left over from the command line can be forwarded:

sc.run('app.py', extra_args=('--debug',))

The child process calls sc.run again on its own. Return values therefore describe the child process.

Host

host chooses the interface to bind:

  • '0.0.0.0': all interfaces; the app is reachable on the LAN.
  • '127.0.0.1': this machine only.
  • 'localhost': this machine only, including IPv6 loopback.

When host is omitted, it follows show_window:

  • show_window=True: 'localhost', because a desktop window is a local session and binding every interface would only earn a firewall prompt;
  • otherwise: '0.0.0.0'.

Opening a native window

show_window=True serves the app and opens it in a desktop window through pyapp-window:

sc.run(
    app,
    port=2201,
    show_window=True,
    window_size=(980, 760),
    window_title='My App',
    window_icon='assets/app.ico',
)

The window is not a browser tab; it is a native webview. Closing it ends the session. With blocking=True, the server is stopped as well.

window_size

window_size is the page viewport, in CSS pixels. A 700x600 window shows 700x600 CSS pixels of the page regardless of the display’s scale factor, so the layout sees exactly the size requested.

window_size=(1200, 900)   # width, height
window_size='maximized'
window_size='fullscreen'

The window manager may crop the requested box when it does not fit the screen. Size the window from the layout the app builds, not from a fixed guess: a form with a known number of rows has a known height.

window_pos

The default is 'center'. A screen position can also be passed the way pyapp-window accepts it. Leave it alone unless the app has a reason to place itself.

window_title and window_icon

window_title sets the OS window title. If omitted, the title is 'Streamlit Canary Application'.

window_icon points to an icon file for the window.

title and icon are shorter aliases:

sc.run(app, show_window=True, title='My App', icon='app.ico')

Platform note

The window backend is provided by pyapp-window. On Windows, its toga backend requires .NET 10. If the runtime is installed outside the default location, point DOTNET_ROOT at it before starting the app.

Blocking behavior

CallableServes in the current thread until stoppedServes on a daemon thread and returns

With show_window=True and blocking=True, run() waits for the window to close and then stops the server.

Stopping an app

  • Press Ctrl+C in the terminal that started a blocking server.
  • With a native window, close the window.
  • With blocking=False, the caller owns the process (for a callable) or the returned child process (for a path target).

The server exposes a /shutdown endpoint, which is how a window session asks the serving child to stop cleanly before falling back to terminating it.

Components

The components are the event-driven library. It has no dependency on Streamlit: every component is a plain Python object that owns reactive Property fields and emits Signals.

Two rules to remember

  1. Build the tree once. The app function passed to sc.run is called once. Components created inside it stay alive for the session.
  2. Change values, not the tree. Attach handlers to signals, then update properties. The runtime sends the difference to the browser.

A first component

import streamlit_canary as sc

with sc.Button('Say hello') as button:
    @button.on_click
    def _():
        print('clicked')

The with block is how a component is added to its parent. Outside a with block it is attached to the current component on the context stack, which is the app root by default.

Namespace

Shared conventions

Sizing

Every component accepts the same size keywords:

sc.Button('Go', width='stretch')
sc.Container(height=320)
sc.Text('x', min_height=40)
  • width / height: an int in CSS pixels, 'stretch', 'content', or 'auto' (where the component supports it).
  • max_width / min_width / max_height / min_height: positive integers or None.

A capped height makes the box scroll. 'stretch' on one axis drops that axis’s min / max bounds.

Visibility

Most components take visible. Text-like components default to 'auto': they show when their content is non-empty and hide when it is blank. A boolean or a bound property is used as given.

sc.Text('')                       # hidden
sc.Text('hello')                  # shown
sc.Text('hello', visible=False)   # hidden
sc.Text('', visible=True)         # shown, but empty

To reserve a line without text, use exactly one space: sc.Title(' ').

Reading and writing

All reactive fields use the same style:

widget.value.get()
widget.value.set(42)
widget['value']          # same as .get()
widget['value'] = 42     # same as .set(42)
widget['on_value']       # same as widget.value.on_change

Binding

sc.bind(source, transform) creates a read-only, derived property. sc.bbind(source) creates a two-way binding for widgets that write back.

sc.Text(sc.bind(state.count, lambda n: 'Count: {}'.format(n)))
sc.NumberInput('Channel', sc.bbind(state.channel))

The Event Driven System

Streamlit Canary replaces Streamlit’s rerun loop with a persistent component tree and a small event protocol.

The old model

In Streamlit, a widget interaction triggers a full script rerun:

click -> rerun script -> rebuild the UI -> diff -> send the page

The cost grows with the size of the script, not with the size of the change. A large app pays the whole price for one checkbox.

The V3 model

In V3, the app function runs once:

start -> run app() once -> build the component tree -> render HTML
click -> WebSocket event -> find the handler -> update properties
      -> send delta patches -> patch the DOM

The app function is never called again for that session. A handler runs only the code registered on the signal that fired.

The pieces

Runtime

sc.run(app_function, port=2201) starts a Starlette + Uvicorn server. The runtime keeps one component tree per session and owns the WebSocket endpoint. It is a no-rerun runtime: there is no script re-execution path.

See Running Apps for sc.run’s full argument list and for opening the app in a native window.

Component tree

Components are nested with context managers:

with sc.Row('center'):
    sc.Text('Left')
    sc.Button('Right')

Each component has an id, a parent, and children. The tree is built once and kept for the life of the session.

Properties

A Property is a reactive value container:

count = sc.Property(0)
count.set(1)
print(count.get())     # 1

Setting a value emits on_change only when the value actually changes. Pass notify=True to force a notification when something outside the value changed but the rendered result still needs a refresh.

Signals

A Signal is a publish / subscribe primitive with no value:

clicked = sc.Signal()

@clicked
def handler():
    print('clicked')

clicked.emit()

Signals may declare payload types:

changed = sc.Signal(int)
changed.emit(42)

Handlers

A component exposes named signals:

with sc.Button('Save') as button:
    @button.on_click
    def _():
        ...

on_click, on_change, on_submit, and the other signals are ordinary Signal objects. A handler runs on a daemon worker thread, so a long operation does not block the WebSocket loop.

Delta patches

When a property changes, the runtime serializes the new value and sends a patch naming the component and the field. The browser updates that field in place. No HTML page is reloaded.

Some elements own client-side state that never reaches the server: expanding an Expander, switching a Tabs panel, opening a Popover. Those interactions are handled entirely in the browser.

Binding values

sc.bind derives a property from one or more sources:

label = sc.bind(state.count, lambda n: 'Count: {}'.format(n))

The derived property updates when a source changes. A Signal may be listed beside the value sources as a trigger: it forces a recomputation even when the value comes out the same, which is useful when the rendered result depends on more than the value.

label = sc.bind(
    (state.items, state.reloaded),
    lambda pair: ', '.join(pair[0]),
)

sc.bbind binds in both directions:

sc.NumberInput('Channel', sc.bbind(state.channel))

The widget mirrors the state, and a user edit writes back into it.

Special markers

sc._self, sc._value, and sc._undefined are sentinel objects used by the kernel. They are not values; they tell a handler or a binding how to resolve something at the moment it runs.

sc._self

Bind sc._self in .partial(...) to receive the signal’s owner:

@state.count.on_change.partial(sc._self)
def _(prop):
    print(prop.get())

For a property, the owner is the Property itself. For a component signal such as button.on_click, the owner is the component:

@button.on_click.partial(sc._self)
def _(btn):
    print(btn.text.get())

Without .partial(...), a handler receives whatever the signal emits. Use sc._self when the handler should read several fields of the owner, or when it needs the handle rather than a snapshot of its value.

sc._value

Bind sc._value to receive the owner’s current value:

@state.count.on_change.partial(sc._value)
def _(value):
    print(value)

This is shorthand for calling .get() inside the handler. It is meaningful only on a signal whose owner holds a value: a Property has one, a plain Button does not.

sc._undefined

A Property declared without a default starts as sc._undefined:

class State(sc.State):
    selection: sc.Property[str]

sc._undefined is falsy. Two consequences matter:

  • sc.bind does not run its transform while the source still holds sc._undefined, because the transform may not accept it.
  • A bound target that needs a defined starting value should be given one explicitly:
label = sc.bind(state.selection, str.upper, default='')

Test for it with identity:

if state.selection.get() is sc._undefined:
    ...

What a handler should do

A handler is the equivalent of the body of an if st.button(...) branch, but it runs only when that event happens. It should:

  • update one or more properties;
  • keep the work short;
  • avoid touching the component tree (create components in app(), not in a handler).
with sc.Button('Load') as button:
    @button.on_click
    def _():
        state.status.set('loading')
        data = load_data()
        state.rows.set(data)
        state.status.set('ready')

Reading a property gives its current value. Writing it schedules a patch.

Ordering and batching

During a single event, property writes are staged and flushed together. A derived property that depends on several sources is recomputed once, after the last declared source has settled. This keeps a multi-field update from producing a chain of intermediate renders.

Client-side interactions

Not every interaction needs the server. The following are local to the browser:

  • opening and closing an Expander;
  • switching Tabs;
  • opening and closing a Popover (the server can still call close());
  • folding a folder row in a tree;
  • highlighting a row.

The server is told only about the results it needs: a new value, a submitted path, a closed dialog.

Session State

State is the base class for application state. It is a PropertyHost: a plain object whose fields are reactive Property and Signal handles.

Declaring state

The simplest form declares fields inside __init__:

import streamlit_canary as sc


class State(sc.State):
    def __init__(self):
        super().__init__()
        self.count = sc.Property(0)
        self.name = sc.Property('')


state = State()

A field may also be declared by annotation. PropertyHost builds one handle per instance:

class State(sc.State):
    count: sc.Property[int] = 0
    name: sc.Property[str]
    reloaded: sc.Signal
  • Property[int] with a class-body value uses that value as the default.
  • Without a class-body value the property starts as sc._undefined (see Special markers).
  • Signal declares no payload; Signal[int] declares one positional payload.

Do not declare a Property instance at class level unless the state class has a single instance. Class-level properties are shared between instances.

Reading and writing

state.count.get()        # 0
state.count.set(1)       # 1, emits state.count.on_change
state['count']           # 1
state['count'] = 2       # 2
state['on_count']        # state.count.on_change

state.count += 1 is not supported by the property object itself. Use the subscript form, which the runtime maps to get and set:

state['count'] += 1

Reacting to changes

@state.count.on_change
def _():
    print('count is now', state.count.get())

A handler may receive the property handle or its current value:

@state.count.on_change.partial(sc._self)
def _(prop):
    print(prop.get())

@state.count.on_change.partial(sc._value)
def _(value):
    print(value)

Binding

A derived value is created with sc.bind:

double = sc.bind(state.count, lambda n: n * 2)

A two-way binding is created with sc.bbind:

sc.NumberInput('Count', sc.bbind(state.count))

See The Event Driven System for the full explanation of triggers, multiple sources, and default=.

Versioning

State tracks a schema version:

class State(sc.State):
    __version__ = 2
    ...

or pass it explicitly:

state = State(version=2)

The version is currently metadata (state.version). It gives the app a place to detect an incompatible state layout and rebuild it.

Lifetime

State lives in the server process for the life of a session. Because the app function does not rerun, a value written in one handler is still there in the next handler.

This also means that state is not rebuilt from the script. If you need a value to reset, reset it explicitly:

state.count.set(0)

Relationship to Streamlit’s session_state

State replaces st.session_state for V3 apps. The two are not synchronized. A V3 app should keep its state in State and pass it to handlers by closure, or store it on the app object.

Option widgets

CheckGroup, RadioGroup, Selectbox, Multiselect, SegmentedControl, and SelectSlider share an options model:

  • options: the choices, bindable;
  • index: the selected position, or None;
  • value: the selected value (a list for multi-select widgets);
  • format: a callable value -> text, or a list of labels parallel to options.

index and value are kept in sync. Setting either one updates the other.

    'Level',
    options=(1, 2, 3),
    value=2,
    format=lambda n: 'Level {}'.format(n),
)

Submitting text

TextInput, TextArea, and NumberInput expose:

  • on_value: the committed value changed (on blur or Enter);
  • on_submit: Enter was pressed (Ctrl+Enter for TextArea);
  • on_editing_finished: editing ended, either by submit or by losing focus.

TextInput additionally exposes on_editing, which fires on every keystroke while the text is still uncommitted.

Layout

Layout components decide where other components go. They are used as context managers; every component created inside the block becomes a child.

with sc.Row('center'):
    sc.Text('Left')
    sc.Button('Right')

Pages

  • Row — horizontal layout
  • Column — vertical layout with a flex weight
  • Container — bordered, sized, scrollable box
  • Expander — collapsible section
  • Grid — explicit rows and columns
  • Tabs — tab bar with one panel per label
  • Dialog — modal dialog
  • Popover — floating panel behind a trigger
  • Floating — sticky corner cluster
  • Space — flexible spacer
  • Bottom — bottom-anchored container

Spacing

The layout uses two spacing tokens:

  • --st-hgap (8px) for horizontal gaps;
  • --st-vgap (16px) for vertical gaps.

A Row spaces its children with the horizontal gap and uses the vertical gap when it wraps. A Container and a Grid use the vertical gap between their children / rows.

Sizing

Layout components accept the shared size keywords. A Container with a fixed height scrolls when its content overflows. height='stretch' fills the parent instead; inside a Row, it makes the column span the row’s tallest sibling.

Floating is an alias of FloatingContainer.

How it behaves

  • Children lay out in a row; the cluster hugs them.
  • The box sticks to its corner of the parent’s visible area, so content scrolls underneath while the box stays put.
  • It keeps its place in the layout (position: sticky, not an overlay), so the parent needs no extra padding.

Where it may go

A floating cluster must sit directly in a vertical layout:

  • a Container,
  • a Popover,
  • a Dialog,
  • or the app root.

Anything else raises ValueError. A Row cannot hold one, because the corner’s horizontal half comes from align-self, which a row would fight.

Authoring order

Sticky positioning can only offset a box from its own flow position:

  • author a top-* cluster as the parent’s first child;
  • author a bottom-* cluster as the parent’s last child.

A bottom cluster also receives margin-top: auto, so it drops to the end of the remaining room.

The data model

data is one map from a name to a sub-map or None:

  • a dict value is a folder; {} is an empty folder;
  • None is a leaf;
  • the map must have exactly one key, which is the root.

Node paths are the names joined with /, for example A/D/G. This is what the location bar shows, and what value contains.

An empty model ({} or None) lists no rows. A model can be handed in later.

Re-rooting

data is bindable. Setting a new model re-roots the tree and clears the selection, because the old paths belong to the old model:

tree.data.set(new_model)

The new model is validated on assignment, so a malformed one raises instead of drawing nothing.

Folding

A folder with children carries a chevron to the left of its row. Clicking it folds the folder open in place; clicking the row itself picks or ticks it. The two gestures are independent.

Multi-select

In the multi modes a folder stands for its whole subtree:

  • ticking a folder drops any picks it covers, then adds it;
  • once every child is picked, the picks fold into the folder itself;
  • unticking a row inside a pick opens the pick one level at a time and leaves that row out.

A folder with only part of its subtree picked draws a half-ticked box.

Root behavior

.. is drawn only after leaving the root. Standing on the root, there is no outside to walk to.

Legacy Streamlit Wrappers (V1)

Caution

The V1 wrappers are no longer exported as sc.* (they left the top-level namespace in 0.5.0). Import them from streamlit_canary.legacy_streamlit_wrappers. For new work, read Components.

Components V1 is the original layer of Streamlit Canary. It is built directly on top of Streamlit and follows the same rerun model: every interaction re-executes the script, and widgets return their current value from that run.

They are still there, under their own module:

from streamlit_canary import legacy_streamlit_wrappers as legacy

value = legacy.toggle_button('Show details')

It remains useful for:

  • small scripts that do not need persistent state;
  • porting an existing Streamlit app with minimal changes;
  • comparing behavior against upstream Streamlit.

It is not the recommended way to build a new app. The rerun model is exactly what V3 removes, and V1 widgets cannot participate in the V3 component tree or its delta patches.

Migrating to the default components

V1 and the event-driven components can live in the same process, but they do not share a component tree. An app should use only sc.* components inside its app function.

The mental model

V1:

import streamlit as st

count = st.session_state.get('count', 0)

if st.button('Increase'):
    count += 1
    st.session_state.count = count

st.text('Click count: {}'.format(count))

V3:

import streamlit_canary as sc


class State(sc.State):
    count = sc.Property(0)


state = State()


def app():
    with sc.Text('Click count: 0') as txt:
        @state.count.on_change.partial(sc._self)
        def _(cnt):
            txt.text.set('Click count: {}'.format(cnt.get()))

    with sc.Button('Increase') as btn:
        @btn.on_click
        def _():
            state['count'] += 1

The differences:

  1. The app function runs once. There is no if st.button(...) branch that runs on the next rerun.
  2. State is explicit. State fields are Property objects, not dictionary entries.
  3. Widgets expose properties and signals. You attach a handler with @widget.on_click or @widget.value.on_change instead of reading a return value.
  4. Updates are pushed. Changing txt.text sends a patch; the browser replaces that text node.

A practical checklist

  • Replace st.session_state with a State subclass.
  • Replace st.button(...) plus an if branch with sc.Button(...) plus @button.on_click.
  • Replace “read the widget’s return value” with widget.value.get().
  • Replace “write a widget’s value by assigning its return value” with widget.value.set(...).
  • Move conditional rendering into a Container(visible=...) or an Expander, rather than skipping code on a rerun.
  • Replace st.rerun() with a state change. A rerun is neither needed nor available in the V3 runtime.

Things that do not translate one to one

  • A V3 component is created once. If a widget should not exist at all, keep it hidden with visible=False instead of not creating it.
  • Layout is built with context managers (with sc.Row(): ...), not by assigning columns to variables.
  • Server-side code inside a handler runs on a worker thread. Keep handlers short, and do not block the event loop for long periods.
